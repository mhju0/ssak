# 싹(Ssak) — 회고

> 2026-09-05 최종 아카이브에 보존한 한국어 초안입니다. 외부 블로그에는 게시하지 않았습니다.
> 본문의 커밋 수는 당시 기록이며, 정확한 종료 시점 집계는 [프로젝트 인계 문서](../PROJECT_HANDOFF.md)를 참고하세요.

**2026-07-15 → 2026-08-02 · 186 커밋 · 의도적으로 종료.**

끝났고 이어가지 않을 프로젝트의 기록입니다. 뭘 하려고 했는지, 먼저 버린 게임은 뭐였는지, 실제로 뭐가 만들어졌는지, Fable은 뭘 잘하고 뭘 못했는지, 그리고 왜 여기서 멈추는지를 담았습니다.

## 1. 애초에 뭘 하려고 했나

목표는 두 개였고, 둘 다 소박했습니다.

1. **게임을 하나 만든다.** 만들어 본 적이 없었습니다.
2. **Anthropic의 Fable 모델로 프로젝트를 통째로 굴려 본다** — 스펙부터 빌드까지 전부 맡겨 보고, 그 워크플로가 실제로 **어디서 깨지는지** 확인한다. 이것도 써 본 적이 없었습니다.

**둘 중 어느 것도 "App Store에 낸다"거나 "유저를 모은다"가 아니었습니다.** 이건 정확하게 못 박아 두고 싶습니다. 제가 세운 목표 기준으로 보면 이 프로젝트는 잘 끝났고, 세운 적 없는 목표 기준으로 보면 실패처럼 보이기 때문입니다. 실패가 아닙니다. **끝난 실험**입니다.

## 2. 먼저 버린 게임

저장소는 **먹(Meok)** 으로 시작합니다. 수묵화 스킬링 RPG였어요. 여섯 개 스킬(낚시, 채집, 요리, 제작, 원예, 그림), XP 곡선, 해금 테이블, 그리고 사용자가 사는 도시의 실제 날씨와 태양 고도에 반응하는 절차적 수묵 월드.

**5일 동안 66개의 커밋**을 쌓았고 마일스톤 M3까지 갔습니다. 그리고 **실제로 돌아갔습니다.** 세로로 긴 두루마리 월드에 시차(parallax) 잉크 레이어가 있었고, 태양 곡선을 따르는 낮/밤이 있었고, 종이에 번지는 비가 내렸고, 관리인 캐릭터가 걸어 다녔고, 11종 어류의 낚시 루프가 끝에서 끝까지 동작했고, SwiftData 영속성까지 붙어 있었습니다.

그런데도 죽였습니다.

솔직한 이유는 이렇습니다. M0–M3까지 나온 시점에서 남은 스코프 — 스킬 세 개 더, 여섯 스킬 전체의 해금 테이블, 방문객 시스템, 갤러리 — 가 *이미 만든 것 전부보다 컸고*, 그때가 5일째였습니다. 첫 게임의 설계 원장에 맞물린 진행 시스템이 여섯 개나 들어가 있으면 안 되는 거였어요. **"야심 차다"를 "좋다"와 헷갈렸던 겁니다.**

**전부 [`meok-archive`](https://github.com/mhju0/ssak/tree/meok-archive) 태그에 살아 있습니다** (66 커밋, 삭제한 것 없음). 버린 걸 뜯어볼 수 있다는 게 핵심입니다 — **뭘 멈췄는지 볼 수 있어야 멈췄다는 말이 신뢰가 가니까요.**

돌아가는 코드를 버리는 건 안 돌아가는 코드를 버리는 것보다 훨씬 어려웠습니다. 그리고 이 저장소에서 제가 옳았다고 제일 확신하는 결정이기도 합니다.

## 3. 싹(Ssak)은 어떤 게임인가

4일 뒤에 다시 시작했습니다. 이번엔 **끝낼 수 있을 만큼 작게** — 창가에 화분 **하나**, 실제 시계를 따라 키우고, 여섯 종을 모으면 끝. **15일에 119 커밋.**

플레이됩니다. 메리골드를 심고, 물을 주고, 내일 다시 옵니다. 압축된 실시간 스케줄(실제 하루 ≈ 식물 일주일)로 눈에 띄게 다른 다섯 단계를 지나가는데, **건강할 때만** 자랍니다. 너무 마르거나 물을 너무 주면 성장이 멈춰요. 오래 방치하면 딱 한 단계만 되돌아가고, 씨앗 아래로는 안 내려가고, 죽지 않습니다. 꽃이 피면 눌러서 선반에 올리고, 다음 씨앗을 고릅니다. 압화 여섯 개를 채우면 정원이 완성됩니다.

**규모** — Swift 파일 59개, 4,066줄, SwiftPM 패키지 3개:

| 패키지 | 역할 |
|---|---|
| `SsakCore` | 순수하고 시간이 주입된 게임 로직 — 성장, 수분, 시듦, 연속 기록, 영속성. UI 없음, 자체 시계 없음. **테스트 39개.** |
| `SsakArt` | 꽃을 전부 SwiftUI `Path`로 직접 그림. 헤드리스 PNG 렌더 루프로 작업. 런타임 아트 엔진 없음. **테스트 4개.** |
| `SsakApp` | 단일 `GardenModel` 리듀서 위의 화면들. **테스트 15개.** |

**테스트 58개, 실패 0** (2026-08-24 확인, Xcode 26.6).

전부 로컬입니다. 백엔드 없음, 계정 없음, 서드파티 의존성 없음, 애널리틱스 없음, 광고 없음, 인앱결제 없음. 사운드도 햅틱도 없는데, 이건 빠뜨린 게 아니라 결정한 겁니다 ([ADR-0001](https://github.com/mhju0/ssak/blob/main/docs/adr/0001-no-sound-no-haptics.md)).

설계는 코드 한 줄 쓰기 전에 **14개짜리 의사결정 원장**(D1–D14, 스펙 부록 A)을 거쳤고, UI는 **완전한 리디자인을 세 번** 갈아엎었습니다. Liquid Glass → 살아 있는 `RoomScene` + 상단 필 내비게이션 → 글래스 키트를 완전히 걷어낸 **한지 압화집**.

## 4. 에이전트 워크플로는 뭘 잘하고 뭘 못했나

프로젝트 전체를 Claude Code + Fable로, 문서로 쓴 스펙과 계획을 따라 굴렸습니다. 저장소 차원의 운영 매뉴얼(`CLAUDE.md`), 도메인 용어집(`CONTEXT.md`), ADR, 그리고 다섯 개짜리 트리아지 라벨 체계(`docs/agents/`)를 뒀습니다. 제가 놀란 순서대로 적습니다.

**진짜 잘했던 것**

- **순수하고 잘 명세된 로직.** `SsakCore`가 이 저장소에서 제일 좋은 코드인데, 동시에 제일 명세하기 쉬운 부분이었습니다. 결정론적이고, 시간이 주입되고, UI가 없어요. 성장/수분/시듦 수학이 테스트 39개와 함께 깔끔하게 나왔고 끝까지 깔끔했습니다.
- **분량 많은 기계적인 작업.** 여섯 종의 벡터 아트를 다섯 성장 단계에 걸쳐 손으로 그리는 건 지루한 종류의 일인데, 여기서는 한 번도 병목이 아니었습니다.
- **기록하는 게 오버헤드가 아니라 핵심 인프라였습니다.** 의사결정 원장과 ADR은 형식이 아니라, **186 커밋 동안 에이전트가 일관성을 유지한 수단**이었습니다. 문서가 애매하면 코드가 틀렸습니다.

**깨진 지점 (증거와 함께)**

- **테스트는 통과하는데 게임이 안 되는 코드를 냅니다.** 이 저장소 최악의 버그예요. `pressAndReplant`가 *이미 수집한* 압화 카드를 눌렀을 때만 도달 가능한 구조라, 첫 꽃은 절대 누를 수가 없었고 여섯 종 수집이 **UI에서 말 그대로 도달 불가능**했습니다. 핵심 루프가 막다른 길이었어요. 그런데 **테스트는 전부 통과했습니다.** [`72c3b95`](https://github.com/mhju0/ssak/commit/72c3b95)에서 수정. **"이 게임에 후반부가 없다"를 잡아내는 테스트 스위트는 없습니다** — 직접 해 봐야만 압니다.
- **변별력 없는 테스트를 씁니다.** [`b68d872`](https://github.com/mhju0/ssak/commit/b68d872)에서 에이전트가 마른 흙 경계의 `0/0` NaN 버그에 회귀 테스트를 붙였는데, 그 테스트가 *고치기 전* 코드에서도 통과했습니다. Swift의 `max(x, y)`가 `y`가 NaN이면 `x`를 반환하거든요. 에이전트는 red-green을 돌았다고 주장하는 대신 커밋 메시지에 **정직하게 적어 뒀고**, 그건 좋은 결말입니다. 하지만 **한 번도 실패한 적 없는 테스트는 회귀 테스트가 아니고**, 그건 읽어야만 알 수 있었습니다.
- **취향은 스펙에서 나오지 않습니다.** UI 리디자인 세 번. 에이전트는 당신이 묘사한 인터페이스를 충실하게 만들어 주는데, 그게 생기가 없습니다. 매 라운드가 저는 스크린샷을 보고 "아니, 이게 아니야"라고 말하는 일이었고, **그 루프는 끝까지 짧아지지 않았습니다.**
- **시뮬레이터 ≠ 실기기.** [`ba0cb00`](https://github.com/mhju0/ssak/commit/ba0cb00) — 시뮬레이터에서는 정확히 자리 잡던 코치마크 스포트라이트가 실기기에서는 대상을 빗나갔고, 컷아웃으로 탭이 새어 나갔습니다.

**제 얘기**

*디자인이 벽이었습니다.* 저는 주로 백엔드를 합니다. 싹이 어떻게 보이고 어떤 느낌이면 좋겠다는 생각은 있었는데, 그걸 머리에서 꺼내 코드로 옮기는 능력이 거의 없었어요. **리디자인 세 번이 측정한 건 게임 로직의 난이도가 아니라 바로 그 간극입니다.** 에이전트는 제가 정확하게 묘사할 수 있는 인터페이스라면 뭐든 만들어 줬습니다. 제가 정확하게 묘사하지 못했습니다.

*제가 병목이 되자, 리뷰를 놓았습니다.* 중반쯤부터 제가 루프에서 제일 느린 부품이 됐습니다. 제가 읽을 수 있는 속도보다 빠르게 코드가 나왔어요. Fable이 며칠만 열려 있을 예정이라 시계와 싸우고 있었고, 저는 속도를 유지하려고 코드 리뷰를 놓았습니다. **위의 최악의 두 가지 — 막다른 길이 된 핵심 루프와 한 번도 실패하지 않은 회귀 테스트 — 는 정확히 아무도 diff를 안 읽을 때 나오는 모양입니다.** 마감을 생각하면 서두른 것 자체가 틀렸다고는 생각하지 않습니다. **실수는 "읽기를 멈추면 안 되는 몇 가지"를 고르는 대신 리뷰를 통째로 놓은 것**입니다.

*spec-first는 빨랐던 것 같습니다.* 스펙 먼저 쓰고 만드는 루프가 코드를 바로 쓰는 것보다 빨랐다고 믿습니다. 다만 이건 **측정이 아니라 느낌**이라고 솔직하게 적어 둡니다. A/B를 해 본 적 없고, 커밋 히스토리는 이것의 증거가 되지 못합니다.

*바꿀 건 도구가 아니라 순서입니다.* 다음엔 실제 레퍼런스 디자인을 먼저 모으고, 코드 한 줄 쓰기 전에 디자이너처럼 생각하겠습니다. 화면 전부, 버튼 전부, 레이아웃, 이게 도대체 어떤 장르의 게임인지까지 구체적으로 매핑한 다음, 거기에 맞춰 디자인하고, 그다음에 코드를 씁니다. 이번엔 스펙 → 코드 → "아니, 이게 아니야"를 세 바퀴 돌았습니다. **다음 건 디자인에서 출발합니다.**

## 5. 한계 — 이건 이런 게 아닙니다

- **App Store에 낸 적 없고, 낼 계획도 없습니다.** 프로비저닝도, 심사도, 개인정보 매니페스트도 없습니다.
- **시뮬레이터 위주로 검증했습니다.** iOS 26 시뮬레이터에서 돌아가고, 일부 폴리싱 패스만 실기기에서 확인했습니다.
- **플레이어 0명.** 저 말고 아무도 안 해 봤습니다. 그러니 "차분하다", "아늑하다"는 주장은 실제 사람에게 검증된 적이 없습니다.
- **사운드·햅틱·알림·iCloud 동기화·날씨/계절 반응 전부 없습니다** — 실수로 빠진 게 아니라 명시적으로 스코프 밖(스펙 §10)입니다.
- **기능 10개를 `wontfix`로 잘랐습니다.** 대부분 먹의 미완성 진행 시스템입니다.
- **긴 호흡은 정의상 검증이 불가능합니다.** 여섯 종을 다 모으려면 실제로 몇 주가 걸립니다. 시계를 앞으로 돌리지 않고 완주를 지켜본 적이 없습니다.
- **재사용 라이선스가 없습니다.** 읽으라고 공개한 거지 쓰라고 공개한 게 아닙니다 — README 참고.

## 6. 다시 한다면 뭘 바꿀까

1. **두 번째 화면을 만들기 전에 루프를 끝에서 끝까지 플레이해 본다.** 막다른 길 버그가 존재한 이유는, 5분만 직접 해 보면 될 걸 초록불 테스트 스위트를 더 믿었기 때문입니다. **게임에서는 테스트 통과가 "동작한다"에 대해 알려주는 게 거의 없습니다.**
2. **멈출 조건을 스펙에 적는다.** 스펙에 성공 기준(§11)은 있는데 *멈춰도 될 만큼 됐다*의 정의가 없었습니다. 그래서 미리 그어 둔 선이 아니라 흥미가 떨어져서 멈췄어요. 먹도 똑같이, 더 시끄럽게 죽었습니다.
3. **스펙이 아니라 디자인에서 시작한다.** 리디자인 세 번이 레퍼런스를 일주일 모으는 것보다 비쌌습니다. 비주얼 방향을 먼저 정하고 화면과 버튼을 구체적으로 매핑한 *다음에* 스펙을 씁니다. 저는 느낌을 묘사해 놓고 인터페이스를 기대했습니다.
4. **뭘 절대 리뷰에서 빼지 않을지 미리 정한다.** 제가 병목이 됐을 때 리뷰를 트리아지하는 대신 통째로 놓았습니다. **"핵심 루프를 건드리는 변경"과 "새로 추가되는 테스트의 assertion"** — 이 두 줄짜리 규칙이면 위의 두 버그 다 잡혔고, 전부 읽는 비용의 몇 분의 일이었을 겁니다.
5. **먹을 5일째가 아니라 2일째에 자른다.** 스코프 문제는 M0가 나오기도 전에 설계 원장에서 이미 보였습니다. 보고도 계속 만들었어요.

## 7. 왜 여기서 멈추는가

**원하던 걸 얻었기 때문입니다.**

게임을 만들 수 있는지, 그리고 AI 에이전트로 실제 프로젝트를 굴리면 어떤 느낌인지 알고 싶었습니다. 이제 둘 다 압니다 — 추상적으로가 아니라 구체적으로, 근거는 §4에 있습니다. 싹은 제가 배우려던 걸 다 배운 지점까지 왔고, 여기서 더 가면 유저도 없고 낼 생각도 없는 스토어를 위해 게임을 유지보수하는 일이 됐을 겁니다.

**관성으로 계속하는 건 먹이 잘못될 뻔했던 방식입니다.** 저장소가 돌아가고, 테스트가 초록이고, 판단 근거가 적혀 있는 상태에서 의도적으로 멈추는 게 더 나은 결말이고 — 5일째에 내렸던 것과 같은 결정을, 이번엔 덜 소란스럽게 한 번 더 내린 것뿐입니다.

저장소는 읽기 전용으로 아카이브했습니다. 빌드되고, 돌아가고, 플레이됩니다. **그거면 끝난 물건입니다.**
